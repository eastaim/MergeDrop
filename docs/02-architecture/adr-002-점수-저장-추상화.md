# ADR-002: 점수 저장을 ScoreService 인터페이스 뒤에 두고 서버 도입을 미룸

## 상태

승인됨 (2026-09-12)

## 배경

게임에 전역 랭킹을 넣을 것인가, 넣는다면 어디에 올릴 것인가를 정해야 했다. AWS나 네이버 클라우드
같은 클라우드에 올리는 경우가 어떻게 되는지도 함께 검토했다.

검토 결과 정리한 것은, **웹 게임의 클라이언트는 어떤 스택으로 만들든 결국 정적 파일**이고 정적
파일을 뿌리는 일은 S3든 GitHub Pages든 기능적으로 동일하다는 점이다. 진짜 갈림길은 호스팅 업체가
아니라 **서버가 필요한가**였다.

| 단계 | 필요해지는 시점 | 구성 | 운영 부담 |
| --- | --- | --- | --- |
| 0. 순수 정적 | 기록이 브라우저에만 있어도 됨 | GitHub Pages / Cloudflare Pages | 없음 |
| 1. 정적 + BaaS | 전역 랭킹, 클라우드 저장 | + Supabase 또는 CF Workers+D1 | 낮음 |
| 2. 정적 + 자체 API | 서버 검증, 자체 계정 | AWS(S3+CloudFront+Lambda+DynamoDB) 또는 NCP | 중간 |
| 3. 실시간 멀티 | 대전, 상태 동기화 | 상시 WebSocket 서버 | 높음 |

0~1단계에서 AWS/NCP를 쓰는 것은 이득이 없다. 똑같은 정적 파일을 올리는 데 IAM, 버킷 정책, OAC,
us-east-1 인증서, CI 역할까지 세팅하고 카드를 등록해야 하며, 결과물은 `git push` 한 번과 같다.
AWS/NCP가 정답이 되는 시점은 2단계부터인데, 그건 게임이 이미 돌아가야 판단할 수 있는 문제다.

## 결정

**0단계로 출시하되, 점수 저장을 `ScoreService` 인터페이스 뒤에 숨긴다.**

```ts
export interface ScoreService {
  getBest(): Promise<number>;
  submit(score: number): Promise<boolean>;
  getLeaderboard(limit: number): Promise<readonly LeaderboardEntry[]>;
}
```

- 현재 구현체는 `LocalScoreService` 하나 (localStorage, 개인 최고 기록만)
- 주입은 `src/main.ts`의 `preBoot` 콜백에서 registry에 넣는 **한 곳**에서만 일어난다
- 게임 코드는 `localStorage`도 `fetch`도 직접 호출하지 않는다

인터페이스가 전부 `Promise`를 반환하는 것은 의도적이다. 로컬 구현에는 불필요하지만, 나중에
네트워크 구현으로 바꿀 때 호출부의 동기/비동기 구조를 다시 고치지 않기 위해서다.

`getLeaderboard()`가 빈 배열을 반환할 수 있다는 것도 인터페이스의 일부다. 호출부는 랭킹이 항상
채워져 있다고 가정하면 안 된다.

## 이유

- **지금 클라우드를 정하면 잘못 정한다.** 트래픽도, 치팅 위험도, 실제로 랭킹을 볼 사람이 있는지도
  모르는 상태다. 이 상태에서 고른 인프라는 나중에 버려질 확률이 높다.
- **미루는 비용이 거의 0이다.** 인터페이스 파일 하나(30줄)를 미리 두는 것만으로 나중 교체가
  구현체 추가 + 주입 한 줄로 끝난다. 반대로 씬에서 `localStorage`를 직접 호출해두면 랭킹을 붙이는
  시점에 게임 코드 전체를 훑어야 한다.
- **출시가 빨라진다.** 서버 없이 배포되므로 CI가 정적 빌드 하나면 되고, 장애 지점도 없다.

## 영향

- 1차 릴리스에 전역 랭킹이 없다. 최고 점수는 그 브라우저에만 남고, 기기를 바꾸면 사라진다.
- `LocalScoreService`의 모든 저장소 접근은 try/catch로 감싸야 한다. 시크릿 모드나 사이트 데이터
  차단 환경에서 `localStorage`는 `null`을 주는 게 아니라 **예외를 던진다**. 읽기 실패는 0으로
  떨어지고 게임은 계속되어야 한다.
- 승격 경로가 열려 있다:
  - **1단계** — `SupabaseScoreService` 또는 `WorkersScoreService` 추가. 몇 시간 규모.
  - **2단계** — `ApiScoreService` 추가 + AWS/NCP에 API 구축. 점수 위조 방지가 목적이라면 클라이언트
    제출 점수를 그대로 믿으면 안 되므로, 그때는 게임 로직 일부를 서버로 옮기는 별도 설계가 필요하다.
    이 ADR의 범위를 넘는다.
