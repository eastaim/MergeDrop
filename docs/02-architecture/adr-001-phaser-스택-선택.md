# ADR-001: 웹 게임 클라이언트 스택으로 Vite + TypeScript + Phaser 3 선택

## 상태

승인됨 (2026-09-12)

## 배경

첫 웹 게임을 만들어 배포하기로 했고, 클라이언트 스택을 정해야 했다.

이 머신의 기존 환경은 Flutter(모바일/웹)와 Python 위주였고, **Node.js도 Homebrew도 설치되어 있지
않았다**. 즉 어떤 선택을 하든 "이미 아는 것을 쓸 것인가, 새로 깔 것인가"의 판단이 따라붙었다.

물리 기반 낙하 머지 퍼즐을 만들 예정이므로 2D 물리 엔진, 스프라이트 관리, 게임 루프, 통합 포인터
입력이 필요했다.

## 결정

**Vite + TypeScript + Phaser 3 (내장 Matter.js 물리)** 를 쓴다.

- Phaser는 `3.90.0`으로 **고정**한다. `npm install phaser`는 4.x를 설치하지만 3.x를 명시했다.
- Homebrew를 설치하고 `brew install node gh`로 툴체인을 갖춘다.

## 이유

세 가지 후보를 비교했다.

| | Vite + Phaser 3 | Flutter Web | 바닐라 Canvas |
| --- | --- | --- | --- |
| 추가 설치 | Node 필요 | 없음 (이미 있음) | Node 필요 |
| 학습 비용 | 새로 배움 | 0 (Sudoku로 검증됨) | 중간 |
| 초기 로딩 | gzip 322KB | 2MB+ | 최소 |
| 2D 물리 | Matter.js 내장 | 없음 (직접 구현) | 없음 (직접 구현) |
| 자료·예제 | 압도적 | 게임용은 희박 | 해당 없음 |
| 모바일 터치 | 포인터 API로 통합 | 가능 | 직접 처리 |

**Flutter Web을 쓰지 않은 이유**가 가장 중요한 판단이었다. 이미 익숙하고 추가 설치가 0이라는
장점이 컸지만, 초기 번들이 2MB를 넘어 "링크를 열면 바로 플레이"라는 목표와 정면으로 충돌한다.
게임용 물리·스프라이트 도구도 사실상 없어서 직접 구현해야 했다. 웹 게임의 핵심 가치가 "설치 없이
즉시"인데 그 지점에서 가장 불리한 선택지였다.

**바닐라 Canvas**는 번들이 가장 작지만 물리 엔진을 직접 만들어야 한다. 낙하 머지 퍼즐은 접촉
판정과 안정적인 적층이 게임성의 전부여서, 물리를 직접 짜면 그것 자체가 프로젝트가 된다.

**Phaser 4가 아니라 3인 이유**: `npm install phaser`는 4.2.1을 설치했지만 3.90.0으로 되돌렸다.
Phaser 4는 렌더러가 새로 쓰인 메이저 개편이라 API가 다르고, 검색되는 예제와 문서가 거의 전부
3.x 기준이다. 첫 프로젝트에서 엔진 API 자체가 불확실 요소가 되는 것은 감수할 이유가 없다.

**Homebrew로 설치한 이유**: 기존 툴체인(Flutter, JDK)이 `~/development`에 압축을 풀어놓는
방식이라 그 방식도 후보였다. 하지만 Node는 이후 업데이트와 `gh` 같은 부수 도구가 계속 따라붙어
패키지 매니저의 이점이 크다고 판단했다.

## 영향

- **번들이 크다.** Phaser 본체 때문에 gzip 322KB에서 시작한다. 게임 코드를 아무리 줄여도 이 밑으로
  내려가지 않는다. 대신 이미지 에셋을 0개로 유지해 총량을 억제한다.
- **Node.js 의존이 생겼다.** 이 프로젝트는 `~/.zshrc`의 Homebrew PATH에 의존한다. 비대화형 셸에서
  `node`를 못 찾는 상황이 실제로 발생했다 (하네스 hook 문제, [작업 메모](../03-notes/2026-09-12-초기-구현과-배포.md) 참고).
- **Phaser 3에 고정되었다.** 4로 올리려면 렌더러·씬 API 마이그레이션이 필요하다. 3.x는 당분간
  유지보수되므로 서두를 이유는 없다.
- Matter.js의 함정을 떠안는다. 충돌 콜백 안에서 월드를 변경하면 안 되고, Matter 게임오브젝트의
  `setScale`은 물리 바디까지 스케일한다. 둘 다 실제로 겪었고 `CLAUDE.md`에 기록했다.
